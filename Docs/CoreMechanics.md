## 1. Аудит универсальности: что реально используется

Основа компонентная: внешний вид, данные типа, состояние экземпляра и поведение разделены. Модели Asuna/ZombieMale не являются контрактом игровой логики. Однако произвольная модель с одним добавленным скриптом не становится готовым игровым объектом: нужны коллайдеры, данные и корректные ссылки.

| Объект | Существующая схема | Что ещё настроить / ограничения |
| --- | --- | --- |
| Подбираемый предмет | `Inventory/WorldItem` + `ItemDefinition` + Collider на корне или дочернем объекте | Своя авторская обёртка модели, тип, количество, worldPrefab типа. Передавать конкретное состояние через `Initialize(ItemStack)`, а не создавать вещь заново. |
| Ящик, шкаф, рюкзак-хранилище | `ItemStorage` + `StorageContainer` + Collider | Слоты/содержимое; для текущего сохранения ещё уникальный `Persistence/SaveIdentity`. Скопированному ящику нужен новый постоянный ID. |
| Дверь / переключатель | `DoorInteractable` / `ToggleInteractable`, общий `Interactable` / `IInteractable` | Ссылки на управляемые части/события; доступность E проверяет `PlayerInteractor`. Их состояние пока НЕ сохраняется. |
| Оружие | `ItemDefinition` → `Weapons/WeaponDefinition`, состояние в `ItemStack` | Магазин/прочность принадлежат экземпляру. `WeaponHitQuery` общий, `PlayerWeapons` — ввод/экипировка игрока, его нельзя ставить на NPC. |
| Еда, вода, простое лечение | Существующий тип предмета + `Player/ConsumableDefinition` в списке `PlayerNeeds` | Применение из рюкзака/хотбара; общий use расширяется `IPlayerItemUseHandler`. Пустая фляга/объём жидкости не реализованы. `PlayerNeeds` требует компоненты игрока, это не универсальные потребности всех NPC. |
| Зомби / враждебный наземный NPC | Корневые `ActorIdentity`, `Health`, `CombatTarget`; `AI/EnemyBrain`, NavMeshAgent и атака по необходимости | Фракции/враждебность, навигационный тип, сенсоры, коллайдеры, анимации. Для ползания — отдельная низкая навигация. Это готовая схема наземного врага, не универсальный мозг для летающего монстра или мирного жителя. |
| Мирный NPC | Общие `ActorIdentity`, `Health`, `CombatTarget` при необходимости боевого участия | Поведение и взаимодействия добавляются отдельно. Фракция сама по себе не создаёт диалог, торговлю или распорядок дня. Не добавлять `EnemyBrain` каждому NPC автоматически. |
| Звук / внешний вид | `ActorAudioEmitter` + профиль, адаптер движения; `PlayerVisual` + определение модели | Настроить профиль и адаптер. Звук AudioSource не заменяет события слышимости `GameplayNoise`. |

Пути таблицы относительны `Assets/Scripts`. Канонические примеры: `Assets/CharacterTesting/Prefabs/CharacterTestPlayer.prefab`, `Assets/Characters/Enemies/ZombieMaleActor.prefab`, предметы `Assets/CharacterTesting/Survival`. Подробный состав актёров — в ActorIntegration, не копировать на новый NPC весь префаб игрока вместе с вводом и HUD.

Что мешает удобному массовому наполнению окружения:

- Нет единого набора пресетов/мастера «подбор / контейнер / разрушаемый объект / NPC» с проверкой всех зависимостей. Существующие setup-скрипты настраивают полигон, а не произвольную карту.
- Взаимодействие на E общее; CM-01 добавил маршрутизатор `PlayerHotbar` и `IPlayerItemUseHandler` поверх оружия/потребления. Готовые инструменты/метательные вещи пока не реализованы.
- Сохранение знает только фиксированный набор состояний. Простое добавление `SaveIdentity` на дверь/монстра не сохраняет его поведение.
- Прочность хранится, но её наличие не означает готовые боевой износ, броню, ремонт или бонусы экипировки.

## 2. По какому принципу работают сохранения сейчас

`Assets/Scripts/Persistence/PlayerSaveSystem.cs` по F5 собирает единый снимок; F9 его восстанавливает, включая загрузку после смерти. Автосохранения, автозагрузки при старте и меню слотов сейчас нет. Доступны также E-консоли этапа 11.

1. Сохраняются позиция/обзор/поза, HP, выносливость и её состояние восстановления, еда/вода, ID экипированного оружия; все `ItemStorage` и `WorldItem` текущей сцены. У вещей — ID типа и экземпляра, количество, прочность и магазин; у добычи ещё transform и активность. Этап 12 добавил XP/ранги/очки и назначения хотбара в тот же снимок.
2. Типы разрешаются через сериализованный каталог `ItemDefinition`, хранилища — через постоянные `SaveIdentity`. Unity instance IDs и ссылки на объекты в файл не записываются.
3. JSON версии 2 записывается в `Application.persistentDataPath/character-stage11.json`: временный `.tmp`, затем замена основного файла, предыдущая версия `.bak`. Версия 1 мигрирует в новый прогресс с прежним оружием в первом слоте. SHA-256 обнаруживает повреждение, не является защитой от читов.
4. До загрузки проверяются версия, сцена, контрольная сумма, каталог, уникальность ID, набор хранилищ и свободное место для капсулы. Замена предметов подготавливается заранее; старые ссылки инвалидируются, события отправляются после общей замены. При ошибке проверки загрузка отказывается до изменения игрового состояния. Повреждённый основной файл не подменяется резервным молча.
5. Сохранить можно живого персонажа на земле вне паркура/замаха/перезарядки. Это ограничения текущего прототипа, будущий планировщик должен учитывать их, а не постоянно выдавать ошибки.

Граница: не сохраняются HP/положение/память AI врагов, двери/переключатели, время мира, квесты и экономика. После перезапуска сцена создаёт этих актёров заново. Добавление/удаление хранилища относительно файла сейчас вызывает отказ загрузки; переход между сценами и потоковая загрузка мира не поддержаны. Дополнительный stateful-компонент на предмете требует своего адаптера состояния.

При `Wallet` на игроке сохранение и загрузка намеренно блокируются: откат предметов без отката денег создаёт дублирование сделок. Снимать guard можно только после совместной атомарной интеграции экономики и миграции формата (Т13 второго разработчика). Не заводить отдельный несогласованный файл денег.

### CM-01–CM-03: хотбар — реализован

Подтверждено пользователем: **5 предметов по умолчанию**, прямой выбор **1–5**, переключение **колесом мыши**, выбросить на **Q**, использовать кнопками мыши: пистолет стреляет, фляга позволяет пить. Количество слотов вывести настройкой с русской подписью/Tooltip; при изменении размера проверить назначения и доступные клавиши. Слоты сверх пяти не получают выдуманные цифровые привязки автоматически.

Действующие правила первой реализации:

- Хотбар — ссылки на `ItemStack.InstanceId` в собственном `ItemStorage`, а НЕ пять новых хранилищ и не копии вещей. Назначать выбранную вещь из рюкзака в слот, заменять и очищать назначение; запретить дубли одного экземпляра в нескольких слотах.
- 1–5 выбирают конкретный слот; колесо циклически проходит пять слотов, включая пустые; пустой слот убирает предмет из рук. Одно колесное деление — один шаг, с учётом трекпада/большого scroll delta. В UI прокрутка не переключает вещь в руках.
- ЛКМ — основное действие: выстрел, удар, выпить/съесть одну единицу. ПКМ — вторичное: для оружия прицеливание; у вещи без вторичного действия ничего не расходует. Удержание ЛКМ не съедает всю стопку: потребление одно на новое нажатие. У автоматического оружия сохранить его режим стрельбы. R — существующая перезарядка живому / возрождение мёртвому.
- Q выбрасывает **одну единицу** активной стопки, индивидуальную вещь целиком; выброс всей стопки остаётся в рюкзаке. Общая проверка места и перенос оригинала — WorldItemDropService: если безопасного места нет, вещь остаётся у игрока.
- Оружие показывает магазин/резерв, стопка — количество, индивидуальный предмет при необходимости прочность. При передаче в ящик, продаже или полном расходе назначение очищается. Частичный расход сохраняет привязку к оставшемуся экземпляру; при split/merge не привязываться к случайному предмету того же типа и не искать по имени/номеру слота.
- Оружие, потребление и прочие действия проходят общий арбитраж: нельзя одновременно стрелять и пить. Определить момент списания и отмены до анимаций; отменённое до применения действие не расходует вещь, завершённое не применяется дважды. Меню, смерть, потеря фокуса, смена предмета, загрузка и паркур учитываются явно.
- `Slot1…Slot5`, `HotbarScroll`, `Drop` используют runtime-копию ввода. Старые Keyboard 1/2 удалены из Previous/Next, D-pad сохранён; ссылки восстанавливаются после замены runtime-карты. Не читать Mouse/Keyboard напрямую в каждом предмете.
- ЛКМ/ПКМ в открытом рюкзаке и при захвате курсора не должны одновременно запускать игровое действие. E остаётся взаимодействием с миром и не дублируется кнопкой использования.
- Список InstanceId и выбранный индекс входят в формат 2. Ссылки разрешаются после замены всех ItemStorage; отсутствующий ID очищает слот. Формат 1 мигрирует: прежнее оружие назначается в первый слот, прочие пустые, без создания вещей.

Реальные компоненты: PlayerHotbar — назначения/HUD/маршрутизация, IPlayerItemUseHandler — расширение использования, WorldItemDropService — общий безопасный выброс. Боевая логика остаётся в `Assets/Scripts/Weapons`, перенос — в Inventory, потребности — в PlayerNeeds. Не дублировать их в FirstPersonController. Все детали API — Hotbar.md.

Проверка готовности: назначить пистолет, топор, еду, воду и пустой слот; пройти 1–5 и колесо в обе стороны; проверить ЛКМ/ПКМ/R/Q. Затем полный рюкзак, частичные стопки, перенос/merge, отсутствие места для drop, смерть/меню/паркур/смена в момент использования. F5/F9 и новый запуск восстанавливают нужный экземпляр с прежними ID/магазином/прочностью; общий запас предметов меняется только на реальное потребление/выстрел. Повторить ввод после повторного Play и замены runtime-карты. Только после этого хотбар считается готовым.

### CM-04: сохранить мир, а не только персонажа

План: общий координатор собирает блоки участников по постоянным ID и типам/версиям, проверяет весь снимок, подготавливает объекты, затем применяет его согласованно. Нужны политика создания/удаления runtime-объектов, отметки уничтоженных объектов, принадлежность сцене/чанку и порядок восстановления ссылок. Текущий `SaveIdentity` лишь идентифицирует хранилище, не решает эти задачи.

Первый набор участников: персонаж/хотбар/предметы, дверь/переключатель, HP и положение NPC с безопасным возобновлением AI; затем согласованный блок Wallet/TraderBudget/остатков торговца из Т13. Не сохранять сырые Transform-ссылки, NavMeshPath, coroutine или скрытую цель как Unity-объект. После загрузки AI перепроверяет путь/видимость, смерть и фракции. Для других сцен/чанков заранее определить политику отсутствующих участников вместо молчаливой потери вещей. При неизвестной версии — миграция или понятный отказ, не частичная загрузка.

### CM-05: автосохранение плюс сохранение по желанию игрока

Трактовка запроса: периодическое сохранение без участия игрока **и возможность сохранить вручную**. F5/F9 остаются, добавляется меню «Сохранить / Загрузить» с датой, сценой и типом слота; автоматическая загрузка при старте — только через явное «Продолжить».

Предлагаемый старт: автосохранение включено, интервал **5 минут активного игрового времени**, три циклических автослота, отдельный quick-save и ручные слоты. Это планируемые значения, не существующие настройки. Интервал в секундах, включение, число автослотов и статус вывести в существующее окно настроек с русскими Tooltip. Time.timeScale=0 останавливает отсчёт; открытый рюкзак сам по себе мир не ставит на паузу.

При истечении интервала запрос становится ожидающим: в воздухе/паркуре/перезарядке/незавершённой операции предметов дождаться допустимого состояния и выполнить один снимок, не накапливать очередь за каждый кадр и не прерывать действие игрока. Показать ожидание и причину длительной задержки; после смерти не затирать последнее живое сохранение. Дополнительные события (контрольная точка, выход, смена сцены) добавлять только после определения их согласованного снимка; аварийное закрытие процесса не гарантирует сохранение.

Авто/ручной режим используют один валидатор и формат. Нельзя обходить guard Wallet или ограничения транзакции ради таймера. Ошибка диска/несовместимый участник — видимое сообщение с ограничением повторов, старый рабочий файл сохраняется. При асинхронной записи только уже собранные неизменяемые данные уходят в фон: Unity API и получение состояния остаются на главном потоке, записи сериализуются. Для большого мира измерить длительность сборки снимка до обещаний отсутствия подвисаний.

Проверки: несколько интервалов, смена автослотов, сохранность ручного файла; ожидание в прыжке и успешное сохранение после приземления; пауза/рюкзак/смерть; повреждённый файл/нет места или доступа/прерванная запись; повторный запуск игры; недоступный Wallet-адаптер; отсутствие дубликатов при торговле и загрузке. Резервный файл предлагать восстановить явно, без незаметного отката прогресса.

| Приоритет | Пробел и полезный результат | Граница / следующий шаг |
