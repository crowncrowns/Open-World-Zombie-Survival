## Что входит в снимок

- Персонаж: прежние поза/обзор/HP/выносливость/потребности, опыт/ранги и хотбар. Базы характеристик не переписываются.
- Весь набор `ItemStorage` и `WorldItem` области: ID, количество, прочность, магазин, Transform и активность. У добычи дополнительно один корневой Rigidbody: наличие, скорость/вращение, масса, гравитация, ограничения и режимы. Физическое тело, добавленное к сценовой добыче поверх префаба (Т2), также восстанавливается.
- Зарегистрированные объекты: постоянный ID, Transform корня, activeSelf, состояние удаления и включённость коллайдеров. Сценовые экземпляры восстанавливаются на месте, сохраняют ссылки/overrides; runtime-экземпляры создаются из явного каталога.
- Актёры: канонический Health, смерть, низкая поза, включение мозга/агента и опора патруля. Отдельный общий блок ActorIdentity сохраняет фракцию/враждебность игрока и NPC.
- Двери: исходный закрытый поворот, текущий/целевой угол, направление и состояние движения. Переключатели: логическое состояние и цвет индикатора.
- Все Wallet области: конечный резерв `long` и infinite-политика TraderBudget. Деньги не отдельный файл/предмет/пул; infinite сохраняет конечный резерв неизменным. Ремонт по-прежнему только материалами.

Не сохраняются произвольные поля всех MonoBehaviour, корутины/пути NavMesh/скрытая цель AI, точный кадр анимации, сложный ragdoll, квесты и время мира. Т5 добавляет выбранный торговый профиль и initialized/соответствие личных storage через WorldTraderSaveAdapter; реальные остатки входят в прежний общий набор ItemStorage. Т6/Т9/Т12 используют этот же снимок для результатов сделок/ремонта и таймеров; интеграция Т13 проверена (TradeRepairIntegration.md). См. TraderProfiles.md.

## Компоненты и создание контента

`Assets/Scripts/Persistence`:

| Компонент | Контракт |
| --- | --- |
| `WorldSaveRegistry` | Один реестр области сцены: сценовые ссылки, ID области, каталог runtime-префабов, проверка полноты |
| `SaveIdentity` | Постоянный ID; `player` зарезервирован для игрока. После публикации не менять без миграции |
| `WorldSaveObject` | Корень сохраняемого объекта; управление существованием и Transform |
| `WorldActorSaveAdapter` | Один существующий Health и безопасное возобновление NPC, не второй запас здоровья |
| `WorldIdentitySaveAdapter` | Существующий ActorIdentity: фракция и отношения, без привязки к имени модели |
| `WorldDoorSaveAdapter` / `WorldToggleSaveAdapter` | Состояние существующих взаимодействий, без повторного Interact |
| `WorldWalletSaveAdapter` | Существующие Wallet/TraderBudget; проверка резерва и режима, уведомления после общего commit |
| `WorldTraderSaveAdapter` | Т5: выбранный профиль и initialized/соответствие трёх личных storage; товары сохраняются прежними слотами, новый seed при load запрещён |
| `WorldRigidbodySaveAdapter` | Один корневой Rigidbody; составная физика требует отдельного адаптера |
| `WorldPrefabDefinition` | Стабильный ID типа, ссылка на авторский префаб, revision структуры |
| `WorldRestorePlan` / `ProspectiveWorldPhysics` | Подготовка объектов и проверка будущей геометрии до изменения настоящего мира |

Сценовый объект: добавить WorldSaveObject, назначить уникальный SaveIdentity, добавить адаптеры нужных механик и включить ссылку в `sceneObjects` реестра. Обычному контейнеру достаточно WorldSaveObject + ItemStorage/StorageContainer; его слоты входят в общий набор. Дочерним ItemStorage нужны собственные SaveIdentity; вложенные WorldSaveObject запрещены. Родительская папка должна оставаться неподвижной, сложный масштаб/сдвиг иерархии не является отдельным сохранённым объектом.

WorldItem уже сохраняется набором добычи: **не помещать его одновременно под WorldSaveObject**. Если предмету добавлено новое stateful-поведение (например, горение/заряд/контейнер жидкости), нужен явный контракт состояния и согласованное расширение загрузчика; один стабильный ID не сериализует автоматически все скрипты.

Runtime-объект: собрать авторский префаб с одним WorldSaveObject на корне, создать WorldPrefabDefinition и включить его в каталог реестра. Создавать через:

```csharp
WorldSaveObject instance = registry.Spawn(definition, position, rotation);
instance.RemoveFromWorld();
```

Spawn назначает новый `runtime-…` ID до Awake/OnEnable и производные ID дочерним хранилищам. Загрузка использует сохранённый ID, не генерирует новый. Добавление/перестановка дочерних хранилищ или несовместимая смена префаба требует увеличения `revision` и миграции. Новая модель не требует копировать контроллер игрока/оружие игрока на NPC.

**Удаление:** сценовый объект удалять через RemoveFromWorld: остаётся неактивная запись (tombstone), старый файл сможет вернуть тот же экземпляр и внешние ссылки. Обычный Destroy сценового корня — ошибка авторинга; сохранение/загрузка откажут, вместо создания неполной копии с потерянными overrides. Runtime-объект также можно уничтожить обычным Destroy; отсутствие становится видно после конца кадра Unity. Для удаления и сохранения в одном кадре использовать RemoveFromWorld. Восстановление файла создаёт недостающие runtime-объекты и убирает лишние; содержимое уничтоженного runtime-контейнера исчезает вместе с ним. Для игрового выпадения лута сначала явно перенести оригиналы предметов.

## Порядок восстановления и ограничения области

1. Проверить checksum/версию/область, каталог, стабильные ID и точный состав сценовых объектов/адаптеров. Неизвестный тип/версия/удалённый сценовый ID — полный отказ. Новые сценовые объекты после выпуска файла требуют миграции.
2. Подготовить недостающие runtime-экземпляры неактивными в отдельной служебной сцене; собрать будущие хранилища. Проверить все предметы/ID/балансы/ранги до переноса ресурсов.
3. Построить геометрические копии будущих дверей/коллайдеров в отдельной PhysicsScene. Проверить позу/опору игрока и живые навигационные капсулы NPC; не использовать текущую закрытую дверь вместо сохранённой открытой. Проверить соответствующий стоячий/низкий NavMesh без телепортации через стену/между этажами. Если сцена изменилась и точка NPC/игрока занята — отказ до изменений.
4. Применить проверенное состояние участников без игровых событий; заменить все слоты/добычу, развитие и резервы персонажа. Старые live ItemStack истощаются, их нельзя повторно импортировать.
5. Активировать нужные объекты, включить навигацию и заново проверить окружение. Только затем публиковать уведомления. Бюджеты и вещи к этому моменту уже согласованы.

Прерываются атаки/перезарядка, очищаются цель, услышанная область и память замеченного входа. Сохраняется опора патруля, не скрытый Transform. Низкая поза восстанавливается до включения агента; текущий ползущий актёр не должен потерять исходные размеры стоя в проверочной копии.

Health при загрузке мира **не вызывает Died/Revived/ActorKilled и их игровые UnityEvent**: иначе выпали бы повторные предметы/награды. Есть Changed и отдельный `WorldStateRestored` для идемпотентного представления. Toggle не повторяет onStateChanged/onInteracted; восстанавливает индикатор и сообщает отдельным StateRestored. Внешние последствия переключателя (свет/механизм/дверь) должны иметь собственное состояние/адаптер, а не повторно выдавать ресурсы из callback.

Сейчас область — одна сцена: path и scope должны совпадать, незнакомые участники не игнорируются. Межсценовые операции денег/инвентарей и потоковый мир требуют общего координатора областей; при обнаружении чужих загруженных кошельков/хранилищ сохранение отказывает. Это явная граница вместо частичного отката. Снимок синхронный; лимиты — 4096 объектов области и 16 МиБ файла. Не объявлять это готовой системой streaming для большого открытого мира.

Новый WorldSaveAdapter: постоянный Key и Version; Capture возвращает DTO JSON, Validate проверяет весь блок без изменения мира; ApplySilent после проверки не бросает исключения и не вызывает игровых событий; Publish только наблюдает завершённое состояние. Не выдавать предметы/деньги/опыт в уведомлениях загрузки. Откат при ошибке Apply участника выполняется до замены слотов; сторонний код с произвольными разрушительными побочными эффектами этим контрактом не поддержан. Публикация сообщений защищена отдельно, её ошибка не объявляет уже применённый снимок «не загруженным».

## Миграция и передача Т13

Версия 1 сначала получает начальное развитие/прежнее оружие в первом быстром слоте, как в этапе 12. Версия 2 без экономики дополняется **текущим** миром: старый файл не содержит прошлого состояния NPC/дверей. При наличии Wallet в области загрузка старых версий 1/2 запрещена: в них нет денег, откат одних предметов создаёт дюп. Сделать новый F5 версии 3; прежний файл остаётся `.bak`. Автоматически обнулять кошелёк или выдумывать прежние сделки нельзя.

Старый blanket guard «любой Wallet на игроке запрещён» заменён проверкой полноты всех Wallet через реестр/адаптеры. Внутренние Wallet.RestoreSavedState/TraderBudget.MarkSavedModeInitialized доступны только проверенному загрузчику, не API торговли. На Т5 в этот же снимок добавлен ключ trader с метаданными профилей, а три личных остатка сохраняются обычными слотами. Т13 подтвердил атомарное восстановление результатов сделок/ремонта и таймеров вместе с вещами/деньгами. Отдельный economy-save и снятие проверки полноты недопустимы.

JsonUtility материализует пустые вложенные DTO: наличие предмета/физического тела определяют occupied/hasBody, а не `dto != null`. Не заменять оригиналы ItemStack методом Copy; внутренние RestoreSaved/ReplaceSavedSlots/RetireForRestore остаются исключительно загрузкой проверенного снимка.

## Полигон и ручные проверки

Setup: **Tools → Character Lab → Set Up CM04 World Saving**, только CharacterTest вне Play. Проверка: **Tools → Zombie Survival → Проверить сохранение мира**. Настройки реестра и адаптеров доступны также во вкладке «Потребности / сохранение» существующего окна актёра. Новые поля имеют русские подписи/Tooltip; значения хранятся в настоящих компонентах.

Консоли CM04: X17/20/23,Z−31. Создание контейнера с припасами X16,Z−27; создание зомби в восточной зоне X56,Z−24; удаление созданных контейнеров. Это тестовые команды, не обычная выдача лута. Контейнер использует подтверждённый `Polygon-Lite Survival Collection/Prefabs/SM_Barrel_Open_01.prefab`; обёртка и определения — `Assets/CharacterTesting/WorldSaving`. Для NPC используется общий ZombieMaleActor.prefab. Vendor, SampleScene и старые станции не заменять.

1. Изменить дверь/переключатель, ранить NPC, начислить рубли и включить infinite у тестового бюджета. Создать контейнер, заполнить/перенести вещи, F5. Изменить всё, удалить контейнер, создать лишний, F9: точные балансы/резерв/вещи и прежний набор объектов.
2. Уничтожить runtime-контейнер, дождаться кадра, загрузить файл: тот же ID/содержимое без копий. Два Load подряд не оставляют лишние объекты/старые импортируемые ссылки.
3. Убить NPC, сохранить, оживить, загрузить: NPC мёртв, XP/лут не повторяются. Сценовое удаление через RemoveFromWorld возвращается загрузкой прежнего файла без смены экземпляра.
4. Сохранить ползущего NPC под настоящей крышей; увести и поднять, загрузить: низкая капсула/тип NavMesh и движение по низкой поверхности. Цель/память входа очищены, домашняя точка сохранена.
5. Сохранённая дверь открыта, текущая закрыта: валидный проход загружается. Если будущая закрытая дверь пересечёт сохранённую позу — отказ. Преграда в сохранённой точке NPC также отказывает без изменения HP/рублей/слотов.
6. В отдельном тестовом файле повредить баланс, Key/Version адаптера, prefab ID/revision или scope: отказ всего снимка. Незарегистрированный Wallet также блокирует операцию. Перезапуск процесса Unity не меняет ID/состояние объектов. Для fast Play отдельно проверять сохранение/загрузку; это не новое меню «Новая игра» и не обещание сброса всех сторонних MonoBehaviour без Scene Reload.

## Т6: сохранение после торговли

Сделки меняют уже сохраняемые ItemStorage и Wallet; нового файла/формата не добавлено. PlayerSaveSystem отклоняет Save/Load при TradeService.IsBusy до изменений, чтобы callback уведомления сделки не запускал восстановление мира. Обычный снимок после завершённой операции сохраняет единый итог предметов и денег. Результаты Т6 и границы проверки: [TradeTransactions.md](TradeTransactions.md). Полный Т13 остаётся отдельным этапом.
