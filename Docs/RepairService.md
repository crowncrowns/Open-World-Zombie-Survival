# Т9 — ремонт за материалы

Т13: [TradeRepairIntegration.md](TradeRepairIntegration.md). Полная цепь ремонта и общего Save/Load проверена с неизменными ID/магазином/рублями и точным списанием материалов. Load закрывает сервис только после успешной валидации; старое предложение ремонта использовать повторно нельзя.

20.10.2026. Т9 выполнен; позднее Т10 заменил проверочную оболочку полноценным [окном верстака](WorkbenchWindow.md). Слоты и защиту брони пользователь отложил: эти этапы их не добавляют. Ниже описан сервис и исторические проверки Т9.

## Проверить в игре

Существующий верстак `T4WorkbenchSession` на CharacterTest получил `RepairWorkbench` через исходный prefab. Текущая авторская позиция экземпляра — примерно **X31,07 / Z−27,55**; она сохранена без перестановки. Подойти, посмотреть на верстак и нажать E. В проверочном окне выбрать свою вещь → «Рассчитать расход» → «Подтвердить ремонт». Escape закрывает окно. Мир продолжает работать, движение и бой блокируются общей сессией Т4. «Улучшить» выключено, списаний нет.

Оружейные детали продаются в профиле `weapons_ammo`: начальный запас 20, цена 80 руб./шт. Бронематериалы — `equipment`: 12, цена 120 руб./шт. Это тестовые цены. Уже инициализированные/загруженные запасы не пополняются изменением профиля; для проверки новых стартовых товаров начать новый запуск без загрузки старого снимка. Ткань использует прежний тип `cloth`, новый дубликат ткани не создаётся. Ремонт сам рубли не расходует.

Для износа оружия использовать существующее применение или тестовые консоли Т8; открытие меню прочность не уменьшает. Пример: пистолет 25/100 требует 3 детали, становится 100/100; его ID и патроны в магазине сохраняются. Целая вещь отказывается ремонтироваться без списания.

## Данные и повторное использование

- `Assets/Scripts/Services/RepairWorkbench.cs` требует существующий `WorkbenchServicePoint`; политика по умолчанию — `Assets/Resources/RepairPolicies/Default.asset`. Пустое поле «Правила ремонта» означает общий ресурс, явная ссылка заменяет его. Для нового физического объекта нужны пригодный Collider и общие настройки доступа ServicePoint; модель произвольна.
- `RepairPolicy` задаёт допущенные категории, рецепты по `ItemDefinition.RepairProfileId` и необязательные исключения конкретного типа. Разрешение `Repairable` и прочность обязательны даже для исключения. Настройки компонента доступны также в общей вкладке «Инвентарь» окна настроек.
- `Assets/Resources/RepairRecipes`: `weapon` — 4 оружейные детали; `textile` — 4 ткани; `armor` — 4 бронематериала + 2 ткани на полное восстановление от нуля. Для каждой строки расход `ceil(полныйРасход × (максимум−текущая)/максимум)`. Любое положительное повреждение требует минимум одну единицу каждой строки.
- Материалы/подборы: `Assets/CharacterTesting/Items/Repair`. Оба новых типа добавлены в общий каталог PlayerSaveSystem исходного prefab игрока. GUID старых ассетов, ID предметов и существующие торговые записи сохранены.
- `Assets/Editor/RepairT9Setup.cs`: Tools → Character Lab → Set Up T9 Repair (No Scene Save). Повторный запуск добавляет только недостающее, не сбрасывает авторские рецепты/товары и не сохраняет сцену. Сохранение пользовательской dirty-сцены остаётся явным действием автора.

## Контракт для второго разработчика и ИИ

Использовать только `RepairService.TryPreviewCost` (чтение), `TryQuote(session, workbench, originalItem, ...)` и `TryExecute(quote, ...)`. Предпросмотр не разрешает ремонт. UI не списывает ресурсы и не вызывает SetDurability. Представление Т10 выделено в WorkbenchWindow под управлением PlayerServiceSession; сохранять этот сервис и общую сессию, без второй экономики/инвентаря.

Котировка одноразовая и связана с SessionVersion, конкретным верстаком, политикой, рецептом, исходным экземпляром/ID, прочностью, магазином и снимком слотов своего рюкзака. Перед commit повторно проверяются доступ, жизнь/дистанция/препятствия, владение, правила, материалы и отсутствие атаки/перезарядки. После изменения правил или рюкзака получить новое предложение явно; не пересчитывать цену молча при подтверждении.

ItemStorage подготавливает все списания до изменения. Commit меняет материалы и прочность того же объекта, затем публикует один Changed. Недостаток хотя бы одного материала ничего не меняет. Чужие хранилища, Copy/snapshot, повторное исполнение, полная прочность, пустые/некорректные рецепты запрещены. Материалы должны быть обычными стопками категории Material с положительным расходом и без повторяющихся строк. Wallet не участвует. Не использовать методы восстановления сохранений для ремонта.

`RepairService.IsBusy` действует до окончания уведомления. Общие ItemStorage locks запрещают реентерабельное изменение, а PlayerSaveSystem отказывает Save/Load до файлов и изменения мира, как при торговле/использовании оружия. Формат сохранения 3 прежний: предмет и остатки материалов уже сохраняются общим снимком; отдельный repair-save не создаётся. Существующие ограничения покрытия мира не отключать.

## Подтверждённые проверки

В отдельной копии Unity 6000.6.3f1: 34 проверки RepairT9Checks и 29 прежних TradeT6Checks прошли. Проверены округление, ноль/полная прочность, несколько стопок, единый Changed с финальными состояниями, запрет повторов и callback-операций/Save/Load, устаревшие прочность/материалы/раскладка/рецепт/сессия, сохранность оригинала/ID/магазина и рублей. Реальный E открыл сессию, события мыши выбрали предмет, рассчитали и подтвердили ремонт в IMGUI. Общие TrySave/TryLoad после ремонта восстановили 100/100, магазин12, тот же ID, остаток деталей1 и баланс321; перед загрузкой прочность/материалы намеренно менялись. Выключение RepairWorkbench и удаление физического верстака за дистанцию после расчёта отклонили подтверждение без расхода. Проверочная сцена и снимки UI находятся вне основного проекта, в `_CodexRecovery/RepairT9-20261020`.

Пользовательская сцена с лесом не сохранялась и не запускалась ради проверки. Изменён исходный prefab существующего верстака и каталог исходного игрока; подключённые экземпляры наследуют компоненты. Т9 не объявляет весь будущий Т13 (все торговые/мировые сценарии) завершённым.
